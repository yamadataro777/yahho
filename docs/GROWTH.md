# 需要・集客・成約から改善する運用

この機能は「仮説 → 根拠の記録 → 集客 → 成約との照合 → 改善 → 再評価」をつなぎます。根拠を登録しただけで需要が実証されたことにはなりません。画面の初期値に閲覧・成約・提携・需要を示すダミーデータはありません。

## 最初に行うこと

1. 管理画面で、対象読者・困っている作業・想定検索語・用途・案内ページを仮説として登録します。「小規模チーム」だけでなく、どの仕事で何に困っているかを記入します。
2. 顧客の質問、検索データ、競合の公開ページなどを、元のURL・観測日時・要約と一緒に登録します。個人名・メールアドレス・非公開の顧客情報を貼り付けないでください。
3. 仮説に対応する集客キャンペーンを作り、生成されたサイトへのリンクを、承認済みの投稿・メールなどで使用します。この機能自体はSNSへ投稿せず、メッセージを送りません。
4. サイト内の訪問・ページ閲覧・診断・広告クリックを確認します。ASPから確定成果を取り込む際、対応するクリックIDが返る場合だけ成約を結び付けます。
5. 改善提案の根拠と件数を確認し、実施した変更を記録します。十分な期間と件数を確保して、変更後の結果を再評価します。

公開には本番Cloudflare設定、提携にはASPの承認が別途必要です。2026-10-28時点の開発環境では調査先への通信許可が未反映で、実際の市場データはまだ取り込んでいません。許可が反映されるまでは、現在のプロキシ制限を回避して収集しません。

## 根拠の種類を混同しない

| 種類 | 分かること | そのままでは分からないこと |
| --- | --- | --- |
| 顧客の質問・発言 | 具体的な困りごとの存在 | 市場全体の大きさ、支払意思 |
| Search Console | 自サイトが検索に表示された回数とクリック数 | 市場全体の検索数、購買や成約 |
| 検索候補 | 検索語や切り口の候補 | 検索数、需要の強さ、売上 |
| 競合ページ | 競合が扱う課題・表現・提供内容 | 競合の売上や成約率 |
| 公式ページ | 製品や制度の公開情報 | 顧客需要、自サイトの提携承認 |

根拠のURLは出典の追跡用です。登録APIはそのURLを自動取得せず、書かれた内容を独立検証したことにもなりません。日時の古い根拠、集計期間の重複、少なすぎる件数を改善の根拠として過信しない設計です。

## 既存の調査結果を取り込む

`node scripts/import-growth.mjs` は、通常はドライランとして変換結果を表示するだけです。`--apply` を付けた場合だけ管理APIへ保存します。先に仮説またはキャンペーンを管理画面に登録してください。ファイル上限は512,000バイト、1回最大200件です。

### 検索候補の取得結果

通信許可が反映された後に、既存の `node scripts/research.mjs --suggest` で記録したJSONを使えます。成功した1検索語を、対応する仮説へ割り当てます。

```sh
node scripts/import-growth.mjs --format research-suggest \
  --file .research/research-実際の取得日時.json \
  --hypothesis 登録済みの仮説ID --query 'Make Zapier 比較' --dry-run
```

取得失敗や空の候補は根拠として取り込みません。検索候補には件数や検索ボリュームを設定できません。取得日時と元のGoogle検索候補URLを保持します。

### Search Console のCSV

自分のサイトのSearch Consoleから、期間を指定したクエリ別CSVをエクスポートします。英語の `Top queries,Clicks,Impressions` または日本語の `上位のクエリ,クリック数,表示回数` を含むCSVに対応しています。指定語と完全一致する1行だけを取り込みます。CTRや掲載順位から件数を逆算しません。

```sh
node scripts/import-growth.mjs --format search-console \
  --file .research/queries.csv \
  --hypothesis 登録済みの仮説ID --query 'Make Zapier 比較' \
  --period-start 2026-10-01 --period-end 2026-10-27 \
  --observed-at 2026-10-28T10:00:00Z \
  --source-url 'https://search.google.com/search-console/' --dry-run
```

日付と出典は実際のエクスポートに合わせて置き換えてください。出典には該当プロパティ・レポートの公開可能な参照URLを使い、認証用トークンを含めません。ファイルの期間をスクリプトが推測することはありません。集計期間は最大366日、未来日・クリック数が表示回数を超える値・同じ検索語の重複行は拒否します。

### 手元の根拠・投稿実績JSON

`--format evidence-json` は下記のレコードの配列を受け付けます。実際の観測値で作成し、未観測の値を埋めないでください。`id` を省略すると、再実行しても変わらないIDを生成します。

| フィールド | 内容 |
| --- | --- |
| `hypothesisId` | 登録済みの仮説ID |
| `kind` | `customer_quote` / `search_console` / `suggestion` / `competitor` / `official_page` |
| `sourceUrl` | 認証情報を含まない公開HTTPS参照URL |
| `observedAt` | 実際に観測したISO日時 |
| `summary` | 20〜2,000文字の要約。観測と解釈を区別する |
| `query` | Search Consoleでは必須の検索語。他の種類では任意 |
| `metrics` | Search Consoleだけで使用する `{impressions, clicks}` |
| `periodStart`, `periodEnd` | Search Consoleの集計期間 `YYYY-MM-DD` |

`--format observations-json` は投稿・キャンペーン側の実績を保存します。各行は `campaignId, sourceUrl, observedAt, periodStart, periodEnd, impressions, clicks` を持ちます。Threadsなどの表示回数・外部リンククリック数を、自サイト内の訪問数とは別に記録します。クリック数と訪問数が一致する前提ではありません。

```sh
node scripts/import-growth.mjs --format evidence-json --file .research/evidence.json --dry-run
node scripts/import-growth.mjs --format observations-json --file .research/campaign-observations.json --dry-run
```

同一仮説・検索語のSearch Console期間、同一キャンペーンの実績期間は重複保存できません。異なるレポートURLを使って同じ期間を二重計上することも避けます。

### 保存する場合

確認後、同じコマンドの `--dry-run` を `--apply` に置き換えます。公開先を `SITE_URL`、管理トークンを `ADMIN_TOKEN` として環境設定に指定してください。トークンをコマンド引数やGit管理のファイルへ書きません。

送信先は設定したサイトと同じオリジンの `/api/admin/growth/evidence` または `/api/admin/growth/observations` だけです。`SITE_URL` は公開HTTPSのルートURL、ローカル開発時は明示した `http://127.0.0.1:8787` などに限ります。既存プロキシとCAを継承し、リダイレクト先へ認証情報を転送しません。

1件ごとに順番に保存します。途中で拒否された場合、それ以前の保存は残ります。同じ入力の再実行ではIDが維持され、既存の同一レコードは二重保存されません。既存IDの内容を変えた取り込みや重複期間は409となり、勝手に上書きしません。エラー出力に管理トークンやAPIレスポンスの本文を表示しません。

## 成約を計測できる範囲

初期状態ではASP発行URLをそのまま使用します。署名付きURLに勝手なパラメータを付けません。クリックと成約を対応付けるには、ASPが動的なサブIDの付与と成果データへの返却を許可していることを確認し、広告のクリックID設定を明示的に有効化してください。

対応するクリックIDを返せない広告の成果は「未紐付け」として集計します。クリック元や直前の閲覧から推測して紐付けません。取消済みの成果を確定報酬から除外できます。ASPごとの認証・通知仕様は提携先の設定が必要で、汎用の取り込み口を実装しただけではASPから自動的に通知されません。

計測拒否設定、JavaScript無効、通信失敗、ブラウザの制限、計測できないリンク操作では記録が欠けることがあります。これは実人数の完全な測定や、全購入者を追跡する仕組みではありません。

## 改善提案と自動運用

日次処理は、AIが接続されていなくても根拠と集計値から改善候補を作ります。基準はこのサイトの初期運用ルールであり、教材の成功法則や統計的な有意差ではありません。

| 状態 | 次の作業 |
| --- | --- |
| 90日以内の顧客の質問・発言、または表示回数があるSearch Console根拠がない | 需要の根拠を集め直す |
| 集客キャンペーンの観測訪問が100未満 | 流入経路を検証し、観測を増やす |
| 有効な提携広告がない | 案件条件と計測の準備を確認する |
| 100訪問以上で広告クリック／訪問が5%未満 | CTAや比較への案内を変更して試す |
| 成約を紐付けられるクリックがない | ASPのサブID対応を確認する |
| 7日以上経過した紐付け可能クリックが30未満、またはその訪問IDが20未満 | 成果承認の遅れを考慮して追加観測する |
| 上記の件数があり、対応する確定成約が0 | 案件条件や案内内容を見直す |
| 上記の件数と新しい需要根拠があり、成約したクリックが3以上、かつ異なる訪問IDが3以上 | 同じ課題の別の切り口を試す |

需要根拠として検索候補や公式ページだけを登録しても、拡大候補にはしません。「成約率」の分母は、7日以上経過し、ASPのサブID対応が明示されたクリックです。計測できない広告や成果待ちの新しいクリックを、成約しなかったクリックとして評価しません。異なる訪問IDは人の数の証明ではなく、繰り返しクリックだけによる判断を抑える目安です。7日経過は成果確定の保証ではなく、実際の承認期間に合わせた判断が必要です。

各提案には根拠のスナップショットと理由を保存します。未実施の同じ提案は新しい集計で更新し、実施済みの変更前の基準値は固定します。状態は提案・実施・見送り・評価済みで管理します。

- **実施**：実際に変えた文言・配置・対象などを記録します。この操作だけでページを書き換えたことにはなりません。変更前30日間の基準値を保存します。
- **見送り**：採用しない理由を記録します。同じ仮説・キャンペーン・改善種別では、翌日以降も再提案や記事の自動優先に使いません。改めて検証する場合は、新しいキャンペーンを作成してください。
- **評価**：実施から7日以上経過してから、変更後の実績を比較します。実施から90日を超えた場合は、詳細計測の保存期間外として409 `observation_window_expired` を返します。新しいキャンペーンで検証を始めてください。足りない件数は「データ不足」として観測中を維持し、後日再評価できます。十分な件数がある場合は改善・低下・変化なしを観測結果として記録します。根拠収集など率で比較できない作業は、設定した観測条件を満たしたかを記録し、改善率を作りません。前後比較は季節性や流入の変化を除去した因果実験ではありません。

自動的に変わるのは記事の編集優先度です。十分な需要根拠と紐付け可能な確定成約がある仮説を、次の記事の対象用途として優先し、選んだ理由を日次履歴に残します。条件に達しなければ既存の診断件数・日替わり選択に戻ります。広告報酬が高いという理由で読者へのおすすめ順位を変更しません。既存ページのコピーの自動書き換え、無断のSNS配信、広告の自動申請は行いません。

記事生成の既存制限（公式情報源の取得、AI接続、品質検査、1日1記事、自動公開の設定）は引き続き適用されます。改善候補が見つかったことと、記事が実際に生成・公開されたことは別々に記録します。

## 保存と運用上の注意

詳細計測は90日で整理し、サイト内の短い訪問を区切るIDを使います。IPアドレス・ユーザーエージェント・参照元の全文・検索クエリ付きの閲覧URLを訪問記録に保存しません。キャンペーンの説明や根拠の要約にも、個人情報や認証情報を含めないでください。

APIに取り込む確定成果はASPで承認されたものだけです。手入力された根拠・集客実績の真偽までこの仕組みが保証するわけではありません。公開後は、実際のレポートと管理画面の件数が同じ定義・期間で一致しているかを確かめてから、改善に使用します。
